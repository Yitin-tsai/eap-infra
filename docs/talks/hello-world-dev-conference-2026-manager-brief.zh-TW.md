# Hello World Dev：主管 1-on-1 快速說明

## 可以直接這樣開場

> 我想分享的不是「AI 幫我寫了一個交易系統」，而是我在單人學習專案裡，怎麼用 AI 建立接近團隊開發的質疑與驗證流程。EAP 是 Java／Spring Boot 的事件驅動交易後端，我把 Product、Architect、Performance、Implementation、QA、Reviewer 分成有權限邊界的角色；每個建議最後都要經過交易正確性、壓測證據和人工決策。演講會用三個真實故事說明：一個最佳化被採用、一個因交易安全被拒絕，另一個原本已完成的取消訂單設計，因為人的質疑而重新設計。

一句話主張：

> AI 的價值不只是加快產碼，而是把「假設、反對意見、驗證、拒絕與決策」變成可追溯的工程流程；最後責任仍在人。

暫定題目：

> **AI 不是自動駕駛：用交易系統把單人開發變成可審查的工程流程**

## 主管快速了解的 30 分鐘結構

| 時間 | 我要讓觀眾得到什麼 |
| --- | --- |
| 0–3 分 | 單人開發最缺的不是產碼速度，而是有人持續反對自己的假設。 |
| 3–8 分 | 用最少的 EAP 背景解釋：訂單、資產、撮合為何需要跨服務一致性。 |
| 8–14 分 | 說明 AI 角色的輸入、輸出、禁止事項，以及人工檢查點。 |
| 14–22 分 | 用「採用、拒絕、人工推翻」三類真實案例證明流程會產生不同決策。 |
| 22–26 分 | 把方法映射回公司的 Jira、ADR、PR、CI、Code Owner 與 change approval。 |
| 26–30 分 | 給可重用模板，收斂到「AI 提供觀點，人承擔決策」。 |

EAP 背景只占約 5 分鐘。它是案例與證據來源，不是把整場變成個人 side project demo。

## 三段可以口語分享的中文故事

### 故事一：數字變快，卻不能採用

> 我曾經測到 Wallet 結算在 autocommit 下，隔離吞吐從大約一萬一提升到兩萬多筆。只看 dashboard，這是一個很漂亮的優化。但 Reviewer 和 QA 角色要求我回答：如果後置檢查失敗，前面的 SQL 還能不能 rollback？重新跑 PostgreSQL 併行測試後，不只發現不能安全回復，也發現買賣角色對調時可能死結。所以最後的決策不是把數字放進 README，而是回復成明確交易，並固定鎖定順序。這讓我學到，AI 如果只被要求「幫我優化」，很容易替錯誤方向加速；必須先給它拒絕修改的權力和正確性門檻。

### 故事二：TPS 的定義比 TPS 本身重要

> 一開始我也會被「每秒送出多少請求」吸引。但交易系統裡，HTTP 202、RabbitMQ 收到事件，甚至 MatchEngine 寫出成交，都不代表使用者的資產與訂單已經一致。我後來把一筆交易完成定義成：MatchEngine、Order、Wallet 三邊 trade ID 完全相同、資產核對正確，而且 queue、DLQ、outbox、inbox 和 retry debt 都清空。用這個標準，目前誠實能說的是同機 648 accepted orders/s 的持續壓力邊界，完整流程約 301 到 310 trades/s，而不是 2,000 completed TPS。我要分享的是，好的 AI 工作流不只是幫你找到更大的數字，也會阻止你說出證據不支持的話。

### 故事三：人問的一句話，推翻已經做完的設計

> 取消訂單第一版讓 Wallet 維護每張訂單剩餘鎖定量，看起來很完整，測試也能寫。但我自己重新扮演 owner 問了一句：訂單不能改量，MatchEngine 又已經是唯一知道成交與未成交餘量的人，為什麼 Wallet 還要複製一份訂單生命週期？這個問題讓整個流程重新回到架構審查。最後 MatchEngine 負責確保同一份剩餘量不會同時被撮合與取消，Wallet 只依成功結果冪等釋放資產，Order 則處理事件亂序。這個故事很適合表達：角色化 AI 可以擴大思考，但真正有價值的轉折仍可能來自人的質疑；流程要允許已完成的實作被重新打開。

## 如果主管只給我 60 秒

> 這場分享會用我自己的事件驅動交易專案，示範怎麼把 AI 從 coding assistant 變成有角色邊界的工程審查流程。我會刻意呈現三種結果：有證據所以採用、數字漂亮但不安全所以拒絕，以及人工質疑後推翻重做。觀眾最後會拿到一個能套用在一般 API、批次或既有系統的模板：先寫問題與假設，限制每個角色能做什麼，用正確性與效能證據驗證，再由人記錄採用或拒絕。專案本身只負責提供真實案例，不會占掉整場內容。

## 明天想請主管給的回饋

- 觀眾比較需要 AI 協作方法，還是交易系統背景？目前我把專案背景控制在 5 分鐘。
- 「採用、拒絕、人工推翻」三個故事是否足以支撐主張？哪一個最有共鳴？
- 公司情境的 Jira／ADR／PR／CI 對照是否需要更具體，還是避免看起來像內部流程分享？
- 技術深度應停在 outbox、冪等與壓測完成語意，還是值得展示 Redis Lua 的競態細節？
- 題目和開場是否清楚表達「AI 輔助審查、人做決策」，而不是宣傳全自動開發？

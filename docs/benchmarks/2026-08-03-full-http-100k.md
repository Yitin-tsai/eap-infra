## 2026-08-03 Historical Validation

## Published Claim

On one development machine, EAP accepted `100,000` SELL and `100,000` BUY orders through HTTP at approximately `1,000 accepted orders/s` in each phase. The run converged into `100,000/100,000` completed trades with identical trade-ID sets in MatchEngine, Order, and Wallet, exact asset settlement, and zero final queue, DLQ, orderbook, lock, or reservation backlog.

This is a single correctness-gated phase result. It is not a production SLA, a repeated median, or a claim of stable `1,300` full-HTTP TPS.

Measurement note: this run used benchmark schema v1. Its correctness gates remain valid, but its completion window included repeated exact trade-ID verification queries while the system was draining. Schema v2 performs low-cost aggregate polling, freezes the business completion timestamp after durable convergence and three drained queue samples, and runs exact set verification afterward. Treat the v1 throughput values below as conservative historical results, not the latest capacity baseline.

## Benchmark Contract

- Contract: `http-matched-trade-completion-chain`
- Run: `GLT_20260803_HTTP_MATCHED_TRADE_COMPLETION_100K_R2`
- Expected trades: `100,000`
- HTTP orders: `100,000 SELL + 100,000 BUY`
- Target input: `1,000 HTTP orders/s` per sequential phase
- Users: `1,000 buyers + 1,000 sellers`
- Workers / max in flight: `128 / 256`
- Service launch: Gradle `bootRun`, load-test profile

SELL orders first pass through Order, Wallet reservation, Order confirmation, and MatchEngine admission. BUY orders then follow the same public path and trigger one-to-one matching. Timing and throughput are reported separately for each boundary.

## Interpretation

This run is stronger reliability evidence than the earlier 15-second staircase because it processes `200,000` public HTTP orders and verifies `100,000` durable trades. It also shows why EAP reports multiple TPS values:

- HTTP acceptance stayed near the configured `1,000 orders/s` in both phases.
- Once BUY processing began, full durable trade convergence was `707.43 trades/s` including final drain.
- Counting the preceding SELL admission phase reduces the complete two-phase rate to `410.16 trades/s`.
- The earlier seeded `1,300` class result starts after valid Order/Wallet state is prepared and must remain a separate claim.

The result does not replace the staircase capacity boundary: the corrected mixed BUY/SELL short-stage boundary remains `1,000 total orders/s` pass and `1,100 total orders/s` fail. The 2026-08-04 schema-v2 run now supplies current-code 100K correctness evidence, but a repeated schema-v2 100K set and a 30-minute steady-state run are still required for a long-duration capacity claim.

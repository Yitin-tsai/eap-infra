# EAP - LLM Context

> Current cross-service contract. Prefer the service README and source code for implementation details; use `docs/architecture.md` for the public architecture.

## Platform

EAP is an event-driven electricity auction backend supporting Continuous Double Auction (CDA) and Timed Double Auction (TDA), built from standalone repositories. Core services use Java 17, Spring Boot 3.5.3, PostgreSQL, RabbitMQ, and Redis Lua.

| Module | Port | Responsibility |
| --- | ---: | --- |
| `eap-order` | 8080 | HTTP order acceptance, order event stream/outbox, durable trade inbox/application, query projection |
| `eap-wallet` | 8081 | asset reservation, explicit-transaction settlement, Wallet outbox |
| `eap-matchEngine` | 8082 | Redis order book, matching, durable `TradeExecuted`, trade outbox, reservation cleanup |
| `eap-common` | - | compiled integration contracts; no business state |
| `eap-mcp` | 8083 | optional control-plane tools |
| `eap-ai-client` | 8084 | optional local LLM client |
| `eap-trigger` | - | legacy Go experiment; still consumes retired `order.matched` and is not in the current core flow |

## Core Event Flow

```text
HTTP BUY/SELL
  -> Order: lifecycle event + OrderSubmitted outbox
  -> Wallet: reserve assets + OrderConfirmed/OrderFailed outbox
  -> Order: persist reservation result
  -> MatchEngine: Redis Lua match or rest order
  -> MatchEngine DB transaction: TradeExecuted + trade_outbox + optional cleanup task
  -> trade.exchange / trade.executed
       -> Order durable inbox + command-side trade application
       -> Wallet explicit-transaction settlement
```

Current routing keys:

| Exchange / key | Consumers |
| --- | --- |
| `order.exchange / order.submitted` | Wallet |
| `order.exchange / order.confirmed` | Order, MatchEngine |
| `order.exchange / order.failed` | Order |
| `trade.exchange / trade.executed` | Order, Wallet |

There is no Order/Wallet completion callback to MatchEngine. `OrderTradeAppliedEvent`, `WalletTradeSettledEvent`, the legacy `order.matched` bus, and MatchEngine completion views are retired.

TDA flow: Order publishes an auction bid, Wallet reserves assets and publishes `AuctionBidConfirmedEvent` through its outbox, and MatchEngine collects and clears bids on a schedule before Order and Wallet consume `AuctionClearedEvent`. Order bid submission and MatchEngine auction lifecycle events currently publish directly to RabbitMQ, so TDA does not inherit the CDA outbox or capacity evidence.

## Completion Contract

A trade is business-complete only when MatchEngine, Order, and Wallet have the same durable `trade_id` set, assets reconcile, relevant order books/reservations are empty, and measured RabbitMQ/DLQ plus durable retry debt drain. Order query projections are rebuildable and do not block the command-side gate.

## Reliability Rules

- Local business state and outbox records commit atomically.
- Consumers ACK after durable handling.
- Duplicate delivery is expected and absorbed by `trade_id`/`order_id` claims and unique constraints.
- Each service owns its retry, inbox/outbox, and failed state.
- AI/MCP modules never own core transaction correctness.

## Current Performance Boundary

The current CDA mixed HTTP lower-bound class is about 700 accepted orders/s, 350 same-window trades/s, and 320 full-lifecycle trades/s on one host. A 2026-08-07 deep diagnostic passed 700 and failed 800 within the stage window while all work eventually converged. MatchEngine's single Spring scheduler worker currently serializes reservation cleanup and trade-outbox polling; scheduler isolation is only a pending experiment. There is no equivalent published TDA capacity result.
